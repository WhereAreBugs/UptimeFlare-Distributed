# D1 行数优化验收

2026-10-05，优化针对 D1 执行元数据里的实际扫描/写入行数。gzip 仍用于网络传输，但字节压缩不能代替行数优化；D1 按扫描行数计读取，索引维护也可能增加写入，见 [Cloudflare D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/)。本轮不修改表结构，不重跑 state-v2 迁移，也不清空历史或探针真实队列。

## 实现

- 200 条以内的样本先在 Worker 内存中一次聚合，D1 接收按五分钟桶、UTC 日、目标和阶段合并的增量；避免多条 SQL 重复分组或排名原始 JSON。迟到失败仍会正确撤销原成功桶对日平均延迟的贡献。
- 累计检查数、失败数、延迟总和与失败阶段改为 `uptimeflare` 表的 `probe-counters:v1:<probeId>` 文档，每批每探针更新一行。缺少的目标条目只在第一次出现时通过主键读取旧累计表并接续，旧行随后冻结。读取端优先使用已有文档，即使激活变量被遗漏也不会回到过期累计值。
- 完整原始结果块的样本上限从 40 提升到 200，仍保留每块 32 KiB、每窗口 128 块及批量 512 KiB 上限。完整协议字段和失败事件继续保留。
- 历史补传不读取当前通知状态；只有新鲜结果且配置有效通知模板的目标读取最新状态，并限定到已分配探针/目标的主键。通知评估只读取最新可达性，不读取累计和历史。
- 无变化通知状态不再写入；新观察、宽限、暂停、维护、恢复和真正通知仍按事务及版本保护更新。重放先检查 receipt，零写入。
- 探针配置读取跳过仅用于页面的自动名称标签查询。公开状态仍来自 KV/边缘缓存，公开首页不依赖 D1。
- 小时清理只读取一次有界的过期桶集合，统计扣减、精确删除和 receipt 在与提交相同的短租约及事务中完成。混合旧累计与新文档的探针分别处理，不重复扣减。

生产激活变量为 `PACKED_PROBE_COUNTERS=1`。计数文档每探针最多 1 MiB、单次读取最多 8 MiB；未知或损坏文档拒绝提交，不 ACK 未持久化结果。首次接续及以后更新均受配置 revision/提交租约保护。已有文档后不能降级到忽略文档的旧代码；离线 legacy 回滚工具明确拒绝此情况。

## 同一负载实测

完整元数据见 [d1-row-budget-results.json](d1-row-budget-results.json)，可重跑 `cd worker && npm test -- --maxWorkers=1 test/row-budget.test.ts`。基线为 `082cddd`，与新代码使用相同夹具：16 个目标、单探针、每批 200 条结果（25 条失败），并存在 10000 行无关 latest 和 10000 行无关五分钟桶。两个集中场景中每目标结果相隔 1 秒，第三场景每目标相隔 300 秒，更接近默认周期的积压。

| 场景 | 原读取 | 新读取 | 读取减少 | 原写入 | 新写入 | 写入减少 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 集中历史补传 | 12800 | 180 | 98.6% | 166 | 142 | 14.5% |
| 集中新鲜结果及通知观察 | 13172 | 448 | 96.6% | 220 | 163 | 25.9% |
| 五分钟间隔积压 | 13015 | 744 | 94.3% | 580 | 563 | 2.9% |
| 已持久化批次重放 | 6 | 2 | 66.7% | 0 | 0 | — |
| 无变化通知评估 | 395 | 347 | 12.2% | 0 | 0 | — |

这不是生产费用或任意负载的固定节省承诺。五分钟积压覆盖更多独立时段，必须保存各时段桶及逐次失败事件，所以整体写入节省明显少于集中场景。累计统计部分合并为一行不意味着整批只有一次 D1 写入。500 个目标或大量持续失败仍可能超过免费日额度；原始、桶、日统计、最新态和索引成本仍存在。没有通过减少采样、丢弃失败、延长默认周期或提前 ACK 获得上述数字。

## 验证及生产边界

Worker 22 个测试文件、199 项回归通过；新增计数文档测试覆盖首次接续、重复/交叠批次、变量遗漏、迟到样本、过期扣减、混合旧探针、事务失败及损坏数据。行数回归同时检查每批检查数/失败数和重放零写入。Python 12 项测试通过，包括拒绝不兼容回滚。类型检查、lint、统一 Worker dry-run、70 项实际产物管理 HTTP 断言、522 项无 D1 公开缓存检查及真实 DO 重建/重放通过。

生产 D1 额度恢复前只发布代码并保持 Cron 及自动部署门禁暂停。已有 state-v2 数据和两台 Go 队列原样保留；无需 Go 协议升级或重迁移。额度恢复后还需验证真实新样本、累计数/历史一致性、ACK 和积压消减，并采集生产 D1 执行元数据；本地结果不能替代这些验收。
